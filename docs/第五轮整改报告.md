## D. 仍未完成（2 项）

### D-1 `booking_no` / `stay_no` / `folio_no` 全局唯一约束

**现象**：三张表的单号列有列级 `UNIQUE`（`sqlite_autoindex_bookings_1`），与 `idx_bookings_no(hotel_id, booking_no)` 组合唯一并存。多店部署时「两个酒店有同号订单」会失败。

**为什么没修**：SQLite 不支持 `DROP CONSTRAINT`，必须重建表（建新表→复制→删旧表→改名→重建所有索引和触发器）。生产库有数据，操作前要 `VACUUM INTO` 备份，`foreign_keys=OFF` 期间并发写入会破坏一致性。**风险高于收益**，需要在无业务数据窗口期做。

**已做的**：`createBookingAction` 改用按酒店查重的 `nextBookingNo()` + 撞号随机后缀，把概率压到极低。

**详见** `docs/已知问题.md` 第一节（含完整 12 步修复方案与风险）。

### D-2 Server Action 无权限时用户看到错误页

**现象**：Next 16 把 Server Action 抛的异常渲染成错误页，用户看不到「无权执行」的可读文案。

**为什么没修**：需要把 `requirePermission()` 拆成 `throw` 和 `return { ok:false }` 两种，涉及 100+ 处 action，改动量大，建议单独一轮。

**安全上没问题**：无权限请求确实被拒且零副作用（A-1 的四重证据）。

**已做的缓解**：页面按钮按权限隐藏，正常路径下无权限用户看不到按钮。

**详见** `docs/已知问题.md` 第二节。

## 这轮暴露的一个方法论问题

新写的 12 套测试抓到 **4 个我自己引入的 bug**（退款方向、原因丢失、额度重复扣减、多租户漏洞）。

其中**多租户漏洞**在第 4 轮就存在，但 35 套旧测试全绿 —— 因为它们在**单酒店库**上跑，
AND/OR 优先级问题在单租户下行为完全正常。

这印证了清单那句「不能只在单酒店演示库里验证多租户」。

**现在的做法**：所有新测试都在副本上**造第二个酒店（999/9999）**验证隔离，
且跨租户测试带**反向验证**（去掉修复后断言结果会变错），确保测试真能捕获回归而不是碰巧通过。
