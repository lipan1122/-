## 一、`booking_no` / `stay_no` / `folio_no` 仍是全局唯一（P2 多租户）

**现象**

`bookings`、`stays`、`folios` 三张表的单号列上有**列级 `UNIQUE`**（SQLite 自动建的
`sqlite_autoindex_bookings_1` 等），同时又有组合唯一索引 `idx_bookings_no(hotel_id, booking_no)`。

在副本库上实测（`scripts/test-occupancy-tenant-isolation.mjs` 同批实验）：

```
hotel 1 已有 BK3588
hotel 999 尝试插入 BK3588
→ UNIQUE constraint failed: bookings.booking_no
```

**根因**

建表时把 `booking_no TEXT UNIQUE` 写成了列级约束，而设计意图是「酒店内唯一」。
`src/lib/channels/booking-no.ts:50` 的注释写的就是「唯一索引按酒店隔离，两个酒店可以有同号预订」——
**注释与现状不符**。

**影响**

| 场景 | 影响 |
| --- | --- |
| 单店部署 | **无影响**（一家店不会自己撞自己） |
| 多店部署（同一库多 hotel_id） | 建单可能失败；正常路径靠 `BK{序号}` 递增侥幸不撞，但并发或数据量错位时会撞 |

**本轮已做的缓解**

`createBookingAction` 原来自己算 `BK${MAX(id)+1+3000}`（**全局** MAX），已改为调用
`src/lib/channels/booking-no.ts` 的 `nextBookingNo(hotelId)`：

- 按 `hotel_id + booking_no` 查重
- 撞号时自动加 3 位随机后缀（`BK3588-472`）
- 20 次重试上限

这**大幅降低**了撞号概率，但没有消除——因为列级 UNIQUE 仍然存在，随机后缀只是把冲突概率压到极低。

**彻底修复方案**

SQLite 不支持 `ALTER TABLE ... DROP CONSTRAINT`，必须重建表：

```sql
-- 以 bookings 为例（stays / folios 同理）
PRAGMA foreign_keys = OFF;
BEGIN;
CREATE TABLE bookings_new (... booking_no TEXT NOT NULL, ...);  -- 去掉 UNIQUE
INSERT INTO bookings_new SELECT * FROM bookings;
DROP TABLE bookings;
ALTER TABLE bookings_new RENAME TO bookings;
CREATE UNIQUE INDEX idx_bookings_no ON bookings(hotel_id, booking_no);
-- 重建所有其他索引和触发器
PRAGMA foreign_key_check;
COMMIT;
PRAGMA foreign_keys = ON;
```

**风险**：
- 重建期间表被替换，任何持有旧表引用的连接会失效
- 必须逐个重建索引/触发器，漏一个就丢约束
- 生产库有数据，操作前必须 `VACUUM INTO` 备份
- `foreign_keys = OFF` 期间如果有并发写入会破坏一致性

**建议**：在没有真实业务数据的窗口期（上线前 / 深夜）用 `scripts/migrate-all.mjs` 加一段幂等迁移来做，
并且先在副本上跑通 + 断言 `PRAGMA foreign_key_check` 返回空。

## 二、Server Action 无权限时用户看到的是错误页而不是「无权执行」

**现象**

Next 16 的 dev / prod 会把 Server Action 抛出的异常渲染成错误页，响应体里拿不到
`FORBIDDEN: 缺少权限 channel.sync` 这种可读文案（dev 下还会被
`TypeError: Cannot read properties of null (reading 'useInsertionEffect')` 盖掉）。

**根因**

`requirePermission()` 是 `throw` 而非 `return { error }`，Next 把它当未捕获异常处理。

**影响**

- **安全上没问题**：无权限的请求确实被拒绝，且零副作用（`test-channel-order-permissions.mjs`
  用四重证据验证过：HTTP 被拒 + 零副作用 + admin 同请求 200 有写入 + 直调生产函数抛 FORBIDDEN）
- **体验上有问题**：用户看到一张错误页，不知道是「没权限」还是「系统坏了」

**本轮已做的缓解**

页面按钮按权限隐藏（`channel-orders/page.tsx` 的 `canSync`），正常路径下无权限用户
看不到按钮，不会去点。

**彻底修复方案**

把 `requirePermission` 拆成两种：
- `requirePermission()` —— 保持 throw（用于「不该发生」的情况）
- `checkPermission()` —— 返回 `{ ok: false }`，action 里返回结构化错误给页面渲染

涉及 100+ 处 action，改动量大，建议单独一轮做。

## 三、`allotment` 语义与清单字面不一致（需业务裁定）

**清单字面**（第五轮 P0-3 第 67 行）：「allotment 设为 2 时显示 2」

**当前实现**（`src/lib/room-stock.ts`）：

```
可售 = min(物理可卖上限, allotment) − 在住 − 预订
```

所以「allotment = 2 时显示 2」只在**没有在住/预订**时成立。
若该房型已有 1 间在住，显示 **1**（2 − 1）。

**为什么这样设计**：

`allotment` 在渠道系统里的语义是「放给渠道的房量上限」，它是**上限**而不是**存量**。
如果 allotment 表示「还能卖 2 间」，那在住/预订就该从它里面扣；
如果它表示「总共放 2 间给渠道」，那扣减逻辑又不同。

当前实现选的是「上限收紧物理可卖量」，理由写在 `room-stock.ts` 注释里：
放量（超售）属于渠道侧策略，物理库存不该被 allotment 放大。

**需要业务确认**：allotment 到底是「剩余可放量」还是「总放量上限」。
确认后再决定是否改成 `- 在住 - 预订`。

## 五、`test-checkout-vd.mjs` 的清理曾因 SQLite 限制失败

**现象**：第一次修改后清理块整个 ROLLBACK，残留 1 条测试入住单 + 1 张账单 + 房间停在 VD。

**根因**：清理 SQL 写的是 `DELETE FROM room_logs WHERE room_id=? ORDER BY id DESC LIMIT 1`，
而 **SQLite 默认不支持 `DELETE ... ORDER BY ... LIMIT`**（需要编译时开启
`SQLITE_ENABLE_UPDATE_DELETE_LIMIT`）。

**已修**：改成 `DELETE FROM x WHERE id = (SELECT MAX(id) FROM x WHERE room_id = ?)`，
并在脚本里留了注释说明这个坑。残留数据也已手工清理干净（验证过：残留 0、房间回 VC）。

## 六、`metrics.ts` 的间夜 SQL 曾有多租户漏洞（已修）

**现象**：`WHERE hotel_id=? AND ... AND x>? OR (status='INHOUSE' AND ...)`——
`OR` 分支绕过了 `hotel_id` 过滤。造第二家酒店 2 张在住单后，酒店 1 的间夜从 21 变 23。

**已修**：给 OR 组加括号，并在 `scripts/test-occupancy-tenant-isolation.mjs` 里加了
**反向验证**（把括号去掉，断言结果会变大到 24），确保这个测试能真正捕获该 bug 而不是碰巧通过。

详见该测试文件第 7 条断言。
