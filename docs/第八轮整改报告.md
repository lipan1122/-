## 一、已修复且有真实数据库证据

### P1-1 商超多商品购物车（真实资金风险）

**问题**：`ShopPOS` 只传 `cart[0].id` + 总件数。

实测后果（矿泉水 1 + 牙刷 1）：
- 按矿泉水 2 件扣库存（牙刷库存没动）
- 金额按 2 瓶矿泉水算
- 流水只记矿泉水
- **牙刷白拿**

**修法**：
- 前端提交完整明细 `[{item_id, qty}, ...]`
- 服务端逐商品校验/扣减/写流水，**任一失败整单回滚**
- `shop_sales` 采用**一行一商品**（不是汇总行）——理由：撤销按行回加库存，汇总行会让库存永远回加不了
- 库存流水写到新表 `shop_stock_flows`（`goods_flows.goods_id` 指向仓库表，和 `shop_items` 是两套 id 空间，混用会把不相干的仓库商品串成流水）

**证据**：`test-shop-multicart.mjs` **121 断言全过**，含三商品场景（A×1+B×1+C×2 → 流水 3 行、库存各扣各的、总金额 = 3.5+10+7.25×2 = 28、库存流水 3 条 `stock_after` 与 `shop_items.stock` 一致）、库存不足时**所有**商品库存一件没动。

### 冒烟发现的 5 个真实功能缺陷（全部已修）

| # | 缺陷 | 后果 | 修法 |
| --- | --- | --- | --- |
| 1 | **会员充值两套账**：`memberRechargeAction` 写 `member_wallet`（guest_name 维度），收银台读 `member_wallet_ledger`（member_id 维度） | 充 1000 后储值余额仍 0 → **钱充了花不出去** | 改调 `rechargeWallet()`；同名歧义拒绝（不猜最早一条） |
| 2 | **手动退款不冲销押金**：`refundPaymentAction` 里押金只有注释 | 退房时 `checkoutAction` 按剩余押金**再退一次** | 补三步冲销 + **逐行处理**（单笔 ≤ 该行余额、总额 ≤ `stays.deposit`） |
| 3 | **挂账账单开不出票**：`issueInvoice` 只放行 `SETTLED`，挂账置 `CHARGED` | 挂给协议单位的账没有公司抬头发票 | 允许 `CHARGED`，可开额度取 `total_amount`（不是 `balance`，挂账后 balance=0） |
| 4 | **出租率两套口径**：`metrics` 对提前退房仍算占用 = 32，夜审 = 29 | 同一营业日两个出租率 | `metrics` 的 `CHECKED_OUT` 改用 `actual_check_out`；真库逐日对账 **0 mismatch** |
| 5 | **AR 报表与挂账台账不互通**：挂账写 `ar_ledgers`，报表读 `ar_accounts`+`ar_transactions` | 挂账后 AR 报表查不到这笔应收 | **双写**（`ar_ledgers` 没有账户/授信概念，只改报表会让两个页面变成两个宇宙） |

### 额外发现：报表中心间夜是第三套口径

**7 处**用 `SUM(folio_items.qty)` 当间夜，而 `qty` 从来没被写过 → 真库**每天都是 0**：

| 日期 | 改前（报表间夜） | 改后 | 实际在住 |
| --- | --- | --- | --- |
| 2026-11-18 | **0** | **27** | 21 在住 + 6 间「11-19/20/21 才退房」的已退房单仍占房 |
| 2026-11-21 | 0 | **21** | 21 |
| 2026-11-22（今天） | 0 | **21** | 21 |

→ `metrics.ts` 新增 `stayNightSlices` / `nightSeries`，7 处全部改调 metrics。
顺带修「散客」渠道按**名字**聚合导致间夜**重复计数**（真有一条 id=6 的渠道就叫「散客」）→ 改按 id 聚合。

**验证**：`/reports?r=biz-daily` 实测间夜 21、出租率 **45.65%**，与房态页、夜审完全一致。

### 顺带修的 2 处测试误判

1. `metrics.ts` 的**注释里**提到被禁写法，静态守卫命中注释 → 改成描述性措辞
2. `guest-match` 的断言把「按姓名**唯一性校验**」误判成「按姓名**定位**」→ 改成精确区分（禁止 `LIMIT 1` 盲取，允许查全部 + 同名拒绝），改完仍能抓到模拟的真问题

## 附：这轮的方法论收获

**冒烟的价值不在「跑通」，在「发现实现与要求不一致」**。

上一轮我把冒烟做成 17 步走完一条订单，全部 ✅。这轮扩到 79 个断言、1001 项表检查后，
**发现 5 个上一轮完全没看到的功能缺陷** —— 而且都不是「代码写错了」，
是「**两个地方各写了一套，从来没对上过**」：

- 会员充值：写 `member_wallet`、读 `member_wallet_ledger`
- 押金退款：`checkoutAction` 有、`refundPaymentAction` 只有注释
- 出租率：夜审算一套、`metrics` 算另一套
- 报表间夜：`SUM(folio_items.qty)` 从来没被写过 → 恒为 0
- AR：挂账写 `ar_ledgers`、报表读 `ar_transactions`

**共同模式是「写一处、读另一处」**。静态检查、单元测试、页面 200 都发现不了，
只有「走一遍完整业务链、然后查数据库里那 13 张表对不对得上」才能暴露。

这也是清单反复强调「测试必须真实打开数据库、不能只做 grep 和页面 200」的原因。
