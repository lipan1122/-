# 渠道直连对接清单（F1）

> 代码已就绪：凭据填进去就能发请求，没凭据走沙箱、不落业务数据。
> 本文列出**每家渠道需要你去申请什么**，以及代码里哪些地方要对着官方文档核对。

## 一、通用前提

所有 OTA 渠道都要求同一套门槛：

| 要求 | 说明 |
| --- | --- |
| 商户资质 | 营业执照、特种行业许可证、消防安全证明、星级/评星材料 |
| 开发者账号 | 在渠道开放平台注册企业开发者 |
| 签约 | 部分渠道需签技术服务协议，少数要交保证金 |
| 接口权限 | 签约后由渠道方开通「房态推送 / 订单拉取 / 状态回传」权限 |
| 门店编码 | 渠道方给的门店 ID（store_id），不是你自己的房号 |

拿到后填到 **系统设置 → 渠道管理 → 对应渠道** 的 `store_id` / `app_key` / `app_secret`，关闭「沙箱模式」，点「测试连接」验证。

## 二、逐家清单

### 携程（Ctrip）

- 开放平台：https://openapi.ctrip.com
- 申请入口：携程商家后台 → 开放平台 → 应用管理
- 需要的凭据：`appKey` / `appSecret` / `storeId`（酒店 ID）
- 代码文件：`src/lib/channels/ctrip.ts`
- **待联调核对**：
  - 端点路径（当前按 `/openapi/v1/...` 结构）
  - 签名算法（当前用通用 HMAC-SHA256 排序拼接，携程实际算法以官方文档为准）
  - 报文包裹结构（当前 `{appKey, storeId, timestamp, nonce, sign, ...}`）
  - 订单字段映射（`orderId` / `checkIn` / `checkOut` 等）

### 美团（Meituan）

- 开放平台：https://openapi.meituan.com
- 申请入口：美团酒店商家中心 → 开放平台
- 需要的凭据：`appKey` / `appSecret` / `storeId`（POI ID）
- 代码文件：`src/lib/channels/meituan.ts`
- **待联调核对**：
  - 美团常见的是 md5 + 时间戳拼接，与当前通用 HMAC **不同**
  - 状态枚举（当前 `CONFIRM` / `CHECKIN` / `NOSHOW` / `CANCEL`，可能是数字码）

### 飞猪（Fliggy）

- 走淘宝开放平台 TOP 网关：https://eco.taobao.com/router/rest
- 申请入口：https://open.taobao.com → 应用管理
- 需要的凭据：`app_key` / `app_secret` / `store_id`（飞猪酒店 ID）
- 代码文件：`src/lib/channels/fliggy.ts`
- **待联调核对（重点）**：
  - TOP 的 `hmac-sha256` 是「key 排序后 key+value 直接拼接」，与当前 `k=v&` 通用结构**不同**，必须改 `topRequest()`
  - 公共参数（`method` / `app_key` / `timestamp` / `format` / `v` / `sign_method`）
  - `*_response` / `error_response` 包裹解析
  - 按状态选 method（confirm / checkin / noshow / cancel）

### 抖音（Douyin）

- 开放平台：https://open.douyin.com
- 申请入口：抖音来客 → 开放平台
- 需要的凭据：`app_id` / `app_secret` / `poi_id`
- 代码文件：`src/lib/channels/douyin.ts`
- **现状（诚实说明）**：
  - 房态推送已实现
  - **access_token 换取未实现**（需要真实凭据才能验证刷新策略）
  - 订单状态回传**返回 UNSUPPORTED**（主动回传接口的权限开通方式和参数没把握，不瞎写）

## 三、其他渠道

去哪儿 / 艺龙 / 美团民宿 / 线下协议 / 直订 —— 代码里走**沙箱模式**，可正常登记订单（手动或导入），但没有直连能力。

## 四、联调步骤建议

1. 先在沙箱模式下跑通「推送房量 → 拉单 → 转预订 → 回传状态」全流程
2. 拿到凭据后，把渠道配置的 `sandbox` 改成 0，`endpoint` 指向渠道给的测试环境
3. 点「测试连接」看返回
4. 用一条真实房型做「推送 1 天 1 间」的最小验证
5. 核对 `channel_sync_logs` 表里每一条报文的 `error_code`
6. 逐步放开日期范围和房型

## 五、出问题先看哪里

- `channel_sync_logs` 表：每次调用的 `status` / `error_code` / `message` / `retry_count`
- 错误码含义：
  - `AUTH_FAILED` 凭据错误 / 签名失败
  - `NOT_CONFIGURED` 凭据没填全或渠道停用
  - `NETWORK` 连接超时 / DNS / TLS
  - `CHANNEL_ERROR` 渠道方业务错误
  - `RATE_LIMITED` 触发限流
- 沙箱模式下 `message` 会带「沙箱模式，未连接真实渠道」

## 六、验收现状

```
node scripts/test-channel-adapters.mjs   → 通过 120 / 失败 0
```

脚本验证了：5 个适配器注册、4 个方法齐全、沙箱幂等且零副作用、负库存被拒、
凭据缺失走 NOT_CONFIGURED（不发请求）、错误码归一、fetch 调用计数 = 0（确认没偷发请求）。

**这不是「已接通」**，是「凭据填进去即可发请求」的骨架。
