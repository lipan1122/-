# 演示库孤儿数据清理记录

> 依据 codex 第五轮最终版清单第 321 行：
> 「如果清理演示库孤儿数据，必须提供备份、清理 SQL 和清理数量」
> 「不能通过删除脏数据掩盖数据一致性问题」

## 一、现象

`booking_rooms` 有 4 条明细指向不存在的预订主单：

| id | booking_id | room_id | status |
| --- | --- | --- | --- |
| 1104 | 814 | NULL | PENDING |
| 1105 | 815 | NULL | PENDING |
| 1106 | 816 | NULL | PENDING |
| 1107 | 817 | NULL | PENDING |

## 二、根因（已追溯，不是猜测）

```
bookings 最大 id            612
sqlite_sequence.bookings    832     ← 813-832 曾被分配、后被删除
孤儿明细 booking_id          814-817  ← 落在被删除的区间内
```

**结论**：这是**第 4 轮修复 `deleteBookingAction` 之前**产生的历史遗留。

第 4 轮修复前，`deleteBookingAction` 只执行：

```sql
DELETE FROM bookings WHERE id = ?
```

而 `booking_rooms` 建表时**没有** `ON DELETE CASCADE`，所以明细变成孤儿。

第 4 轮已修复为在同一个事务里先删明细（见 `src/app/(main)/bookings/actions.ts:425-434`）：

```ts
tx(() => {
  run(`DELETE FROM booking_rooms WHERE booking_id = ? AND hotel_id = ?`, [id, user.hotelId]);
  run(`DELETE FROM bookings WHERE id = ? AND hotel_id = ?`, [id, user.hotelId]);
});
```

**所以现在的代码不会再产生新的孤儿。**

## 三、备份

清理前已备份（含 `-wal` / `-shm`，避免恢复时不一致）：

```
data/pms.db.bak-orphan-<HHMMSS>
```

恢复方式：

```bash
cp data/pms.db.bak-orphan-XXXXXX data/pms.db
rm -f data/pms.db-wal data/pms.db-shm   # 必须删，否则与备份不一致
sudo systemctl restart pms
```

## 四、清理 SQL

```sql
DELETE FROM booking_rooms
 WHERE NOT EXISTS (
       SELECT 1 FROM bookings b WHERE b.id = booking_rooms.booking_id
 );
```

（按 `NOT EXISTS` 而不是写死 id —— 这样如果库里还有别的时间点产生的孤儿也一并清掉，清理后重跑幂等。）

## 七、这件事的教训

孤儿数据不是「删掉就好」—— 它证明**曾经有一条写入路径是错的**。

如果只删数据不修写入路径，过一段时间又会冒出来，而且没人知道为什么。

所以处理顺序应该是：
1. **先追溯根因**（哪个动作产生的、什么时候修过）
2. **再确认当前代码不再产生**（读代码 + 找测试）
3. **最后清理存量**（备份 + SQL + 数量）
4. **补防回归检查**（体检项 + 测试断言）

这次 1-4 都做了。
