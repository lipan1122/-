## 二、测试抓到的真实缺陷（已修）

### P0 小程序下单完全没做 `request_id` 幂等

**测试实测**：同 requestId 顺序提交 2 次 → **2 张订单**（BK3003/BK3004）；并发 2 次 → **2 张**。

**影响**：网络超时重试 / 连点 → 重复订单，前台重复排房，客人可能被重复收款。

**修法**：
- `bookings` 加 `mini_request_id` + 部分唯一索引（5 处同步）
- 读键（`body.requestId` / `body.request_id` / 头 `x-request-id`），非法直接 `BAD_REQUEST`（**静默忽略 = 退化成没有幂等**）
- **先查重（鉴权+配置之后、业务校验之前）** → 命中即返回原订单 `replayed:true`
- 同事务写入；并发撞唯一索引 → catch 后重查按重放返回
- 跨用户撞键 → `409 REQUEST_ID_CONFLICT`（**不回吐别人的单号/金额**）
- 前端改用 `state.submit`，失败重试复用同一个键，成功后才换新

**修复后**：顺序提交新增 1 张且第二次 `replayed:true`；并发「1 次新建 + 1 次重放、两次都 200」。

### P1 10 个接口不检查小程序配置

**测试实测**：`mini_program_config` 为 0 行 / `enabled=0` 时，这 10 个接口仍返回 **200**：
`bind`、`bookings`（列表+下单）、`member`、`member/ledger`、`member/unbind`、`notifications`、`notifications/read`、`breakfast`、`invoices`

**影响**：管理员停用小程序后这些接口照常可用。

**修法**：加 `miniConfigBlocked()` 共享检查。**logout 保持可用**（退出是清理凭据，停用后连退出都拒会让客户端继续持有 7 天有效 token，风险窗口反而变长）。

**另加静态回归门**：枚举全部 26 个 route.ts，要求每个都过配置检查（防止以后新加接口再漏）。

### P2 会员中心返回完整姓名

`/api/mini/member` 返回 `张三` 而非 `张*` → 改成 `maskGuestName`。

### P2 login 也返回完整姓名（测试没覆盖，我补的）

`/api/mini/login` 第 159 行 `guestName = guest.name` → 改成 `maskGuestName`。

**前端注意**：返回的是「张*」形态，**不能用它预填真实姓名输入框**（否则提交上去就是「张*」）。

### P2 下单接口是唯一没有限流的写接口（我补的）

`POST /api/mini/bookings` 会**真实占房量**，不限流的话脚本可以批量建单把房卖光 → 加 10 次/分钟（与取消/改单/续住同档）。
