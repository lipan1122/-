> 适用：`/opt/pms` 上的云栖 PMS（VPS 106.52.92.24，systemd 单元 `pms`，端口 3100）
> 最后更新：2026-11-23（首次完成**真实恢复演练**，见第 5 节）
> 结论先放这里：**备份文件能打开 ≠ 能恢复。这份手册是唯一被演练验证过的恢复路径。**

## 1. 备份

### 1.1 什么时候备份

| 时机 | 命令 | 说明 |
| --- | --- | --- |
| **每天定时**（当前**还没装**，见 8.1） | `node scripts/backup-db.mjs` | 内容没变会报「无需备份」，不浪费磁盘 |
| 改数据之前 | 同上 + 先看一眼 `--dry-run` | 比如要跑修复脚本、要改账 |
| 部署之前 | `node scripts/backup-db.mjs` | 出事能回到部署前 |
| 恢复之前 | 恢复脚本**自动**做 | 见 2.2 |

`VACUUM INTO` 是在线快照：**不需要停服务**，也不会阻塞业务写入。

### 1.2 备份存在哪

```
/opt/pms/data/backup/
  pms.2026-11-23T14-36-37.db    ← 本脚本生成，纳入保留策略
  pms.2026-11-23T14-27-34.db
  latest.json                    ← 最近一份的清单（时间/大小/sha256/行数）
  pms.before-fix-oversell.*.db   ← 各修复脚本的一次性快照，永不自动删除
  pms.db.bak-deposit-*           ← 同上
```

**两类别混在一起，清理时务必分清**：
- `pms.<YYYY-MM-DDTHH-mm-ss>.db` → 本脚本管的，保留最近 10 份（`--keep` 可改）
- 其它名字 → 某次危险操作前的现场证据，**脚本永不删**，要删只能手工

### 1.3 命令

```bash
node scripts/backup-db.mjs                 # 备份一次
node scripts/backup-db.mjs --dry-run       # 只看会做什么，零副作用
node scripts/backup-db.mjs --keep 20       # 保留 20 份
node scripts/backup-db.mjs --force         # 内容没变也强制生成
node scripts/backup-db.mjs --json          # 机器可读（cron/监控）
```

### 1.4 每次备份校验什么

产物出来后会重新打开校验，任何一项不过就 **exit 4 并标记「这份备份不可信」**：

| 校验项 | 依据 |
| --- | --- |
| `PRAGMA integrity_check` | 必须是单行 `ok` |
| 表数 | 必须等于源库表数（当前 93） |
| 核心表齐全 | users / rooms / stays / folios / folio_items / payments / guests / bookings |
| 关键行数 | 逐表对比源库，**备份不得比源库少**（少了说明快照被截断） |
| 外键悬空 | 记录条数（本项目无外键声明，正常恒为 0） |
| sha256 | 写进 `latest.json`，恢复时用来确认「拿的就是那份」 |

### 1.5 latest.json 长什么样

```json
{
  "generatedAt": "2026-11-23T14:36:37+08:00",
  "file": "pms.2026-11-23T14-36-37.db",
  "sizeBytes": 1736704,
  "sizeHuman": "1.7 MB",
  "sha256": "ee65f9ce603fad2957dd5abfe78522a6...",
  "tableCount": 93,
  "counts": { "users": 4, "rooms": 46, "stays": 200, "folios": 200,
              "folio_items": 446, "payments": 213, "guests": 62,
              "bookings": 651, "room_types": 7, "booking_rooms": 490,
              "ar_accounts": 5, "op_logs": 665 },
  "integrity": "ok",
  "foreignKeyViolations": 0,
  "keep": 10
}
```

恢复后拿 `counts` 对一遍，就知道恢复的库对不对。

## 2. 恢复

### 2.1 三条铁律

1. **先停服务**。服务在跑时恢复，旧进程会把缓存/旧事务写回新库，结果是「库换了但数据还是旧的」，比不恢复更糟。
2. **恢复前一定有备份**。脚本会自动做，但如果你是手工 `cp`，先自己备一份。恢复错了还能回去，全靠它。
3. **恢复后必须跑迁移**。备份是「某个时间点的库」，可能缺后来新增的表/列 —— 不跑迁移就是一片 500。

### 2.2 脚本替你做的六件事

```bash
node scripts/restore-db.mjs <备份文件> [--force] [--dry-run]
```

| # | 动作 | 说明 |
| --- | --- | --- |
| 1 | **三重校验备份** | ① 16 字节 SQLite 魔数（挡掉 0 字节/HTML 错误页/未解压的包）② `integrity_check` + 表数 ≥ 阈值 + 核心表齐全 ③ 核心表行数（users/rooms 不能为 0）+ 与 latest.json 的 sha256 比对 |
| 2 | **服务占用检测** | `systemctl is-active pms` + 扫 `/proc/*/fd` 看有没有进程打开这个库。**不自动停服务**（那是运维决策），检测到就拒绝执行并打印停服务命令 |
| 3 | **恢复前备份** | `VACUUM INTO data/backup/pms.before-restore.<ts>.db`；当前库已损坏时退化为原样 `cp` 保底 |
| 4 | **清 WAL** | 先 `wal_checkpoint(TRUNCATE)` 再删 `-wal/-shm`。**不做这步会「恢复了但数据没变」**：旧 WAL 会被 SQLite 回放到新库上 |
| 5 | **原子替换** | 先复制成 `.restore-tmp-<pid>` → 校验 sha256 → `rename` 覆盖。不会出现「复制一半断电，目标库变半截文件」 |
| 6 | **恢复后校验** | `integrity_check` + `foreign_key_check` + 逐表行数与备份比对 + 拿 `schema-full.sql` 对比**缺几张表**（明确告诉你要不要跑迁移） |

**退出码**：`0` 成功 / `1` 用户取消 / `2` 文件不存在 / `3` 备份校验不过（拒绝，目标库一字节未动）/ `4` 服务占用（拒绝）/ `5` 恢复过程失败。

### 2.3 恢复后必做（按顺序）

```bash
cd /opt/pms
node scripts/migrate-all.mjs          # ① 幂等迁移：补表/补列/补索引（老备份必跑）
node scripts/sync-schema.mjs          # ② 按 schema-fingerprint 补齐散落在页面里的表
node scripts/rebuild-unique-constraints.mjs --check   # ③ 只检查单号约束
node scripts/preflight-db.mjs         # ④ 38 项数据一致性体检（必须 0 严重）
node scripts/health-check.mjs --no-persist            # ⑤ 业务体检（房态/账务/积压）
node scripts/post-deploy.mjs          # 或者直接跑这一条，它包含 1~5
sudo chown -R ubuntu:ubuntu /opt/pms/data   # ⑥ 归属回服务用户，否则 readonly database
sudo systemctl start pms              # ⑦ 起服务（旧进程还开着旧库，必须重启）
```

## 3. 三种场景

### 场景 A：误删数据（服务正常，只是数据错了）

**特征**：页面能开，但某几张单/账单没了，或者余额不对。库文件本身是好的。

**不要**直接恢复整库 —— 那会把「误删之后新产生的正常数据」一起抹掉。判断标准：
- 误删后**没有新业务写入** → 整套恢复（下面步骤）
- 误删后**已经有新业务** → 别整库恢复。从备份里**导出那几张表**再合并：
  ```bash
  # 把备份挂成另一个库，只取需要的数据
  sqlite3 data/backup/pms.2026-11-23T14-36-37.db \
    ".mode insert stays" "SELECT * FROM stays WHERE id IN (101,102);" \
    > /tmp/recover-stays.sql
  sqlite3 data/pms.db < /tmp/recover-stays.sql
  ```

**整套恢复**：
```bash
cd /opt/pms
sudo systemctl stop pms
node scripts/restore-db.mjs data/backup/pms.2026-11-23T14-36-37.db --force
node scripts/migrate-all.mjs
sudo chown -R ubuntu:ubuntu data
sudo systemctl start pms
```
验证见第 5 节检查清单。

### 场景 B：库文件损坏（打不开 / 500 / `malformed`）

**特征**：
```
Error: database disk image is malformed
Error: attempt to write a readonly database
```
或者服务日志刷 `SQLITE_CORRUPT`。

1. **先保现场**（别急着覆盖，证据只有一份）：
   ```bash
   cd /opt/pms
   sudo systemctl stop pms
   cp -a data/pms.db data/pms.db.corrupt-$(date +%Y%m%d-%H%M%S)
   cp -a data/pms.db-wal data/pms.db.corrupt-$(date +%Y%m%d-%H%M%S)-wal 2>/dev/null
   ```
2. **试抢救**（有时只是索引坏，数据还在）：
   ```bash
   sqlite3 data/pms.db "PRAGMA integrity_check;"     # 看报什么
   sqlite3 data/pms.db ".recover" | sqlite3 /tmp/rescued.db   # 能捞多少算多少
   ```
3. **正常恢复**：
   ```bash
   node scripts/restore-db.mjs data/backup/pms.<最后一份好的>.db --force
   node scripts/migrate-all.mjs && node scripts/sync-schema.mjs
   sudo chown -R ubuntu:ubuntu data
   sudo systemctl start pms
   ```
   > 目标库损坏时，脚本的「恢复前备份」会自动退化为 `cp` 原样保存（VACUUM 读不了坏库），
   > 那份文件**不能直接恢复**，只是现场证据。真正救命的是恢复前的正常备份。

### 场景 C：整机重装（VPS 没了 / 要换机器）

> 备份在 `data/backup/`，**和数据库同一块盘**。整机没了备份也没了 —— 这是当前最大风险（见 8.1）。
> 所以第一步永远是「先把备份拿到别的机器」。

1. **取走备份**（旧机器还活着时）：
   ```bash
   # 本地（Windows/MSYS2）
   scp ubuntu@106.52.92.24:/opt/pms/data/backup/pms.2026-11-23T14-36-37.db ./
   scp ubuntu@106.52.92.24:/opt/pms/data/backup/latest.json ./
   ```
   旧机器已经挂了 → 只能换到最后一份手动下载的备份（所以 8.1 的异地备份必须补上）。

2. **新机器装代码**：
   ```bash
   sudo bash deploy-vps.sh          # 装 Node/依赖/代码/systemd/env
   # 注意：这一步会建一个空库并跑完 post-deploy
   ```
   > 若想直接用自己的备份，先 `PMS_SKIP_INIT=1` 之类的手段并不存在 —— 正确做法是
   > 先让 deploy 跑完（服务能起），再按下面替换库。

3. **灌回备份**：
   ```bash
   sudo systemctl stop pms
   cd /opt/pms
   node scripts/restore-db.mjs /path/to/pms.2026-11-23T14-36-37.db --force
   node scripts/migrate-all.mjs && node scripts/sync-schema.mjs
   node scripts/preflight-db.mjs        # 必须 0 严重
   sudo chown -R ubuntu:ubuntu data
   sudo systemctl start pms
   ```

4. **检查 .env**（新机器会生成新的 `SESSION_SECRET`）：
   - 换了 SESSION_SECRET = 所有人被登出，这是正常的
   - `PMS_ALLOW_HTTP=1` 要保留（HTTPS 没配时 Cookie 才生效）
   - `PMS_DEMO_LOGIN=0` / `PMS_DEMO_SEED=0` 公网必须关

5. **别忘了**：腾讯云安全组放行 TCP 3100、`systemctl enable pms`（deploy 脚本已做）。

### 4.2 或用 systemd timer（更可控，日志进 journal）

```bash
sudo tee /etc/systemd/system/pms-backup.service >/dev/null <<'EOF'
[Unit]
Description=云栖 PMS 数据库备份
[Service]
Type=oneshot
User=ubuntu
WorkingDirectory=/opt/pms
ExecStart=/usr/bin/node scripts/backup-db.mjs
EOF

sudo tee /etc/systemd/system/pms-backup.timer >/dev/null <<'EOF'
[Unit]
Description=每天 03:15 备份 PMS 数据库
[Timer]
OnCalendar=*-*-* 03:15:00
Persistent=true
[Install]
WantedBy=timers.target
EOF

sudo systemctl daemon-reload
sudo systemctl enable --now pms-backup.timer
systemctl list-timers pms-backup.timer
sudo systemctl start pms-backup.service && journalctl -u pms-backup -n 20 --no-pager
```

## 5. 演练记录（2026-11-23，首次真实演练）

> 这是**唯一一次**做过「破坏 → 恢复 → 验证能跑」的完整演练，全程在 `/tmp` 副本上，
> 生产库 `/opt/pms/data/pms.db` 未被触碰（演练结束仍 93 表 / integrity ok / dashboard 200）。

### 5.1 做法

1. 生产备份 → `pms.2026-11-23T14-27-34.db`（93 表 / 1.7 MB / sha256 `1a5b47ed…`）
2. 用 `sudo cp -al /opt/pms /tmp/pms-restore-test` 建副本（`node_modules` 硬链接、`.next` 真实复制），
   库用上面那份备份，`3102` 端口另起一个 Next 实例（生产是 3100）
3. 记录**破坏前**指纹（表数/行数/dashboard 关键数字）
4. 在副本库上**故意破坏**：
   ```sql
   DELETE FROM payments WHERE id IN (SELECT id FROM payments ORDER BY id DESC LIMIT 60);
   DELETE FROM folio_items WHERE id IN (SELECT id FROM folio_items ORDER BY id DESC LIMIT 100);
   DELETE FROM bookings WHERE id IN (SELECT id FROM bookings ORDER BY id DESC LIMIT 120);
   ALTER TABLE guests DROP COLUMN note;
   DROP TABLE op_logs;
   ```
5. 先验证安全门：服务在跑时 `restore-db.mjs` **拒绝执行**（退出码 4）✅
6. 停 3102 → `restore-db.mjs --force` → 起 3102
7. 对比**破坏后 / 恢复后**指纹，并跑 38 项体检 + 业务体检

### 5.3 演练暴露的四个真实问题（都已修或已记录）

1. **`cp data/pms.db` 会丢数据**：副本第一次用 `cp` 建，`payments` 比生产少 8 行、`op_logs` 少 36 行 ——
   因为 WAL 模式下最新写入还在 `pms.db-wal` 里。**这就是必须用 `VACUUM INTO` 的实证。**
2. **副本被误判成生产库**：在 `/tmp/xxx` 里跑脚本时 `cwd/data/pms.db` 恰好是副本，老判据会误报
   「生产库路径」。已改为 `/tmp` 下一律按演练处理。
3. **生产 systemd 服务被误算成「占用副本库」**：`pms` 单元 active 与 `/tmp` 副本无关。
   已改为只在目标库就是 `/opt/pms/data/pms.db` 时才计入占用。
4. **`/opt/pms/data` 被改回 `root:root`**（并行 sudo 操作导致）：症状极具误导性 ——
   服务照常读写（句柄是 chown 之前打开的），**只有新建文件失败**，
   备份报 `unable to open database: .../backup/.tmp-xxx.db`。
   已给 `backup-db.mjs` 加「目录可写预检 + chown 修复命令」。

## 7. 常见坑（都踩过）

| 现象 | 真正原因 | 处理 |
| --- | --- | --- |
| 恢复了但数据没变 | 旧 `-wal` 被回放到新库 | 脚本已处理（checkpoint + 删 wal）。手工恢复时也必须删 `pms.db-wal/-shm` |
| `database is locked` | 服务没停 / `next build` 多 worker 抢 SQLite 锁 | 停服务；构建期已用 try/catch 容错 |
| `no such table: shop_sales` | 恢复的是老备份，没跑迁移 | `node scripts/migrate-all.mjs && node scripts/sync-schema.mjs` |
| `attempt to write a readonly database` | `data` 归属不是 ubuntu | `sudo chown -R ubuntu:ubuntu /opt/pms/data` |
| `unable to open database: .../backup/.tmp-xxx.db` | 备份目录不可写（常因并行 sudo 改了 owner） | 同上 chown；新脚本会预检并提示 |
| 页面 500 但库是好的 | 恢复后没重启服务（旧进程开着旧 inode） | `sudo systemctl restart pms` |
| 所有人被登出 | 换了 `SESSION_SECRET` 或恢复了旧 `sessions` 表 | 正常现象，重新登录 |

## 8. 已知风险与待办

### 8.1 ⚠ 没有定时备份（最高风险）

`crontab -l` 空、`systemctl list-timers` 里没有备份任务。当前所有备份都是**手工触发**的。
→ 配法见 4.1 / 4.2。**这是唯一一条「不做就会在某天丢掉全部数据」的待办。**

### 8.2 ⚠ 备份与数据库同盘

`/opt/pms/data/backup` 和 `pms.db` 在同一个分区。整机/磁盘挂掉 → 全没。
→ 必须补异地备份（4.3）。

### 8.3 备份目录里混着 13 份历史快照（约 25 MB）

命名不统一（`pms.before-*` / `pms-before-*` / `pms.db.bak-*`），脚本不自动删。
→ 确认业务数据没依赖它们之后，手工清理一次。

### 8.4 `fix-room-status.mjs --apply` 不是严格 0 变更

实测每次跑都会 UPDATE 21 行（值不变，先把 OC 重置再设回）。
**影响**：部署瞬间有极短的房态抖动窗口；WAL 会被写一次。
→ 建议改进成「只更新有差异的行」；在此之前，`post-deploy` 里的这一步在生产高峰时段慎跑。

### 8.5 备份没有加密

`data/backup` 是明文的，里面有客人姓名/手机号。谁拿到文件就等于拿到全部客史。
→ 异地存放时必须加密（`age` / `gpg`），或至少放私有 bucket。

### 8.6 演练只覆盖了「库坏了」，没覆盖「整机重装」

本次演练证明了「有备份就能恢复出一个能跑的服务」，但**没有在全新机器上跑过场景 C**。
→ 下次维护窗口建议用一台临时 VPS 完整走一遍场景 C。
