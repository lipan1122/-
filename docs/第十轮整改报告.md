## 一、已修复且有真实数据库证据（5 项）

### P0-1 会员储值卡支付 100% 崩溃（**充的钱一分都花不出去**）

**现象**：`cashier/actions.ts` 查 `SELECT guest_id FROM folios`，但 **`folios` 表没有 `guest_id` 列**（只有 `stay_id` / `guest_name` / `room_no`）→ 任何「会员储值卡」支付都抛 `no such column: guest_id`。

**为什么一直没发现**：`check-round4-coverage.mjs` 对 P1-9 的两条断言只是
`includes("会员储值卡")` / `includes("consumeWallet")` 的**字符串 grep**，
从来没跑过一次储值卡支付 —— **静态自查把 100% 崩溃的路径判成了「已落地」**。

**修法**：改用 `folios.stay_id → stays.guest_id` 的 join（不改表结构 —— 账单本身不该冗余客人 id）。

**证据**：新增 `test-wallet-pay.mjs` **13 断言**，真跑一遍：充值 1000 → 储值卡付 300 → 余额 700 / payments 1 条 / 账单 balance 0。

### P0-2 押金被房费吃掉时，退房不冲销 → 真库残留 6800 元

**现象**：`checkoutAction` 把整段冲销包在 `if (refundCash > 0)` 里，而
`refundCash = min(max(0, -balance), 押金)`；`balance >= 0` 时**一条都不冲**。

**真库实测**：

| 项 | 修前 | 修后 |
| --- | --- | --- |
| `CHECKED_OUT` 残留押金 | **11 张 / ¥6,800** | **0 张 / ¥0** |
| `SETTLED` 仍挂 DEPOSIT 明细 | **3 张 / ¥2,100** | **0 张 / ¥0** |
| `SETTLED` 余额非 0 | 3 张（-44/-64/-26） | **0 张** |
| 已退房但账单仍 OPEN | **5 张** | **0 张** |

**修法**（选 B：押金先抵扣房费、余额退现金；与 A「全额退押金、房费另收」**净额相同**，
但 B 不需要真实退款接口，且不锁死 A）：
- `refundCash` = 只退「多收的钱」
- `depositOffsetToRoom` = 押金里被房费吃掉的部分
- **无论 `balance` 正负，退房后 `stays.deposit = 0`、DEPOSIT 明细全清零**

**迁移** `scripts/fix-deposit-residual.mjs`（`--check` / `--apply`，自动备份，幂等）：
写 8 笔 `DEPOSIT_REFUND`（合计 **-3,334**：退现金 3,334 / 抵扣房费 1,966）+ 19 条 `op_logs`。
本地与 VPS 各执行一次，复核 **0 处待修复**。

### P1-3 押金退款报表还在用 `remark LIKE '%押金%'`

**修法**：抽出共享常量 `DEPOSIT_REFUND_MATCH_SQL`：

```sql
p.kind = 'DEPOSIT_REFUND'
OR p.kind = 'DEPOSIT'
OR ( p.kind IS NULL AND (p.remark LIKE '%押金%' OR p.remark LIKE '%预收%'
    OR op.kind = 'DEPOSIT'
    OR (op.kind IS NULL AND (op.remark LIKE '%押金%' OR op.remark LIKE '%预收%'))) )
```

- **kind 优先**，只有 `kind IS NULL` 的历史行（库里 174 条）才看备注
- 与 `lib/folio.ts` 的 `isDepositPayment` / `LEGACY_DEPOSIT_REMARK`（`/押金|预收/`）**逐字同义**，全项目一套判定
- **同一常量被状态列复用** → 「状态」和「金额」永远读同一批流水

**状态从「按订单是否在住推算」改成三态**（在压 / 部分退 / 已退），由区间内真实退款流水决定。

**实测**（区间 2026-11-01~30）：31 笔 ¥18,452 / 退款 8 笔 ¥3,334 / 23 在压 3 部分退 5 已退，
**逐笔已退合计 3,334 == 退款表 3,334**；
卡片 **押金总额 18,452 = 在压 15,118 + 已退 3,334**（恒等式成立）。

### P1-4 `request_id` 幂等只覆盖「收款」

**补 4 个 action**：`addChargeAction` / `refundPaymentAction` / `addDepositAction` / `checkoutAction`。

**页面**：`CashierPanel.tsx` 加 **6 处**隐藏字段（退房/入账/加收房费/收款/押金/退款），
三级 UUID 降级 + **每操作各持一枚键** + 成功才换新。

**证据**：新增 `test-cashier-idempotency.mjs` **63 断言**，含**两个子进程真并发**同 `request_id` 只成一笔、
跨酒店同 `request_id` 各成一笔（唯一索引按 `hotel_id` 分区）。

### P2-5 无权限页面显示「操作失败」+ React error #441

**根因**（关键）：生产构建把 Server Action 异常**脱敏成只剩 digest**，
`error.tsx` 的 `FORBIDDEN` 文本匹配**永远命中不到**。

**修法（方案 A，不依赖错误文案）**：
- `session.ts` 加 `checkPermission`（结构化返回）+ `requirePermissionOrRedirect`（无权限 redirect）
- 新建 `/no-permission` 页：显示「没有该操作权限」+ 权限点代码与中文名 + 去权限矩阵
- `canAccess` 加 `AUTHENTICATED_ONLY_PATHS = ["/no-permission"]` 放行
  （否则被 `(main)/layout.tsx` 二次踢回 dashboard，**等于没做**）
- **覆盖**：`/reports` 页面 + 收银台 10 个 action
- **未覆盖**：其余 100+ 处仍显示「操作失败」（方案 A 的已知限制，逐页迁移）

### 附带修的 2 个（验收 agent 发现）

**远期房态「剩 N 间」虚高 21 间**（两个独立 bug 叠加）：
1. `stays` 查询带 `AND expect_check_out > firstDate` 过滤 → **逾期未离店的客人被整条滤掉**
   （演示库 21 张在住单 `expect_check_out` 是 11-14~11-18，都早于区间起始日）
   → `stays` 查出来是空的 → `occupied = 0` → 显示 46 间全空
   → **前台按 46 卖会超卖 21 间**
   **修法**：去掉这个过滤。`status='INHOUSE'` 就代表客人还在，房间就占着。
   与 `metrics.ts` / `room-stock.ts` 口径一致（三处都刻意不看 `expect_check_out`）
2. `dayStats` 用 `rows.length` 当总数，**没扣 OOO/LOCK、没读 allotment** → 补齐

**实测：46 → 25/24/5**（与房态页 25 一致）

**新建预订页可售数虚高**：`COUNT(*) FROM rooms WHERE status='VC'` 不扣已排房预订 →
改用 `todayRoomTypeStock()`，标签从「可订数」改成「今可订」。

## 附：这轮的方法论收获

**「静态自查」会给出虚假的安全感。**

这轮最严重的两个 bug，都是「静态检查通过、运行时崩溃」：

1. **储值卡支付**：`check-round4-coverage.mjs` 用 `includes("会员储值卡")` 判定「已落地」，
   但那段代码查了一个**不存在的列** —— 100% 崩溃，且从第 4 轮起就一直坏着。
2. **押金残留**：`test-deposit-kind.mjs` 的 53 断言全绿，但没人验「退房后 `stays.deposit` 是否归零」——
   于是真库悄悄积累了 11 张单、6800 元。

**共同点**：断言写的是「代码里有这个东西」，而不是「跑一遍看结果对不对」。

这轮补的两个测试（`test-wallet-pay` / `test-cashier-idempotency`）都是**真跑一遍完整链路**，
第一次跑就抓到了 bug —— 这正是它们该做的事。

另一个观察：**并行开发下「同一个文件被两边改」不是合并冲突，是两套语义并存**。
这轮 `test-allotment-semantics.mjs` 里同时存在旧口径和新口径的断言，跑一遍才发现。
