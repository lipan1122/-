## 0. 结论摘要（先看这里）

1. **页面级：没有 > 1 秒的页面，也没有 > 3 秒的阻塞级页面。**
   101 个 URL（24 个关键页面 + 68 张报表 + 5 个宽区间报表 + 4 个重参数页面）全部返回 200，
   中位数最慢的是 `reports?r=room-biz-daily&from=2025-01-01&to=2026-12-31` = **421.58 ms**，
   其次是 `/rooms/forecast`（59.22 ms）和 `/orders`（36.37 ms）；其余全部 < 30 ms。

2. **当前页面耗时主要不是 SQL 慢，而是 HTML/RSC 体积。**
   `room-biz-daily` 宽区间一次吐 **3.6 MB HTML**（46 房 × 2 年逐日矩阵，约 3.3 万行），
   页面上 78 条 SQL 合计只有 ~12 ms，**421 ms 里绝大部分是渲染 + 传输**。
   真正 SQL 最慢的是 `/rooms/forecast` 的「排房候选房」查询：**28.23 ms**，占该页服务端耗时的一半以上。

3. **唯一确认的 N+1 在 `/inhouse`**：
   `blankCandidates.map(s => missingRoomDates(...))` 每张在住单查一次库（页内 5 条 SQL 之外再乘在住数）；
   同时 `(SELECT id FROM folios WHERE stay_id = s.id ...)` 因为漏了 `hotel_id`，对每行都全表扫 `folios`
   （`SCAN folios`），现有 `idx_folios_stay(hotel_id, stay_id)` 用不上。

4. **14 条全表扫描（大表）**，集中在 `op_logs`（`date(created_at)` 函数导致索引失效）、
   `channel_orders`（缺 `(hotel_id,status)` 索引）、`payments`（缺 `(hotel_id,folio_id)` 索引）、
   以及 joins 漏 `hotel_id` 导致的 `folios` 全表扫描。

5. **7 个并发场景的数据一致性全部通过**（39 条断言 0 失败），
   说明收钱 / 收押金 / 退房 / 排房 / 夜审在「数据不写坏」这一层是可靠的。
   **但发现 4 个真缺陷**：
   - **P0 业务缺陷：只订房型、不指定房间时没有任何库存校验 → 会超卖**（串行点击就会，和并发无关）；
   - **P1：并发夜审 2/3 个请求 500**（UNIQUE 冲突未翻译）；
   - **P1：并发建单 4/5 个请求 500**（冲突校验在事务外，唯一索引兜底后直接抛错）；
   - **P2：并发改房态时 `room_logs.from_status` 全是旧值**，日志流转链不连续（`changeRoomStatus` 未包事务）。

6. 5 个必跑测试全部通过：`perf-baseline` / `test-concurrency` / `test-cashier-idempotency` /
   `test-room-action-idempotency` / `smoke-business-flow`，合计 0 失败（见第 7 节）。

## 1. 测试方法

### 1.1 页面响应时间（curl）

- 登录：`POST /api/login`（admin/admin123）拿 `pms_sid` Cookie，之后所有页面带 Cookie 请求；
- 每个 URL：**先预热 1 次**（避免首请求冷缓存/连接建立），再连续 5 次，
  用 `curl -w "%{time_total}"` 记录秒数，**取 5 次中位数**，同时记录 min/max 与响应体大小；
- 全部请求串行（并发 1），避免给 3100 叠加负载；测前等待服务就绪，服务重启/构建期间自动重试；
- 报表清单不写死：脚本从 `src/app/(main)/reports/page.tsx` 的 `REPORTS` 注册表解析，
  当前共 68 张；另加 5 个宽区间变体（`from=2025-01-01&to=2026-12-31`）压出真实 SQL 成本。

> 口径说明：这是「单用户、本地、生产构建、热缓存」的基线，不是 p95/压测。
> 它回答的是「打开这个页面要等多久」，不包含公网延迟，也不代表 50 人同时用时的排队时间。

### 1.2 SQL 热点（只读副本 + EXPLAIN）

1. `data/pms.db --VACUUM INTO--> .tmp/perf-<时间戳>/data/pms.db`，副本设 `PRAGMA query_only=ON`；
2. 静态扫描 `src/app/**/page.tsx`，抽出所有 `all()` / `get()` 里以 `SELECT/WITH` 开头的模板字符串
   （共 61 个页面文件、379 条可执行 SQL；12 条因带 `${}` 插值/无法静态执行而跳过）；
3. 逐条 `EXPLAIN QUERY PLAN` + 在副本上实测（先跑 1 次，未超 120 ms 再跑 2 次取中位数）；
4. 标记：`SCAN <大表>`（≥200 行）、`CORRELATED`（相关子查询）、`USE TEMP B-TREE`；
5. 另外用「循环体内出现 all/get，或循环体调用的 helper 内含 all/get」识别 N+1。

### 1.3 并发压测（真并发，多进程）

- `VACUUM INTO` 副本 → 主进程造夹具（房型/房间/入住单/账单/订单/5 个前台账号 + 1 个店长）；
- 用 `node:child_process` **spawn N 个独立进程**，每个进程注入 `globalThis.__pmsDb` 指向同一副本，
  把 `next/headers` 等换成本地桩，**import 真实的 `src/app/(main)/**/actions.ts`**，
  再用不同前台的 session 调用 action —— 与页面提交表单完全同一条代码路径；
- 所有 worker 通过 `WORKER_GO_AT` + `Atomics.wait` **对齐到同一毫秒开跑**，
  避免「启动有先后」把并发变成串行；并发数 3~5（不打挂 3100，本测试根本不经过 3100）；
- 结束后**只信数据库**：核对金额合计、房态、流水条数、日志次数、占用明细、`night_audits` 条数等，
  不把「有没有报错」当结论。

### 3.3 N+1 查询

脚本识别到 **1 处确认的 N+1**：

- `/inhouse`（`inhouse/page.tsx:203`）
  ```ts
  const blankNights = blankCandidates
    .map((s) => { ... const missing = missingRoomDates(s.folio_id, from, today); ... })
  ```
  `missingRoomDates()`（同文件 129 行）内部执行
  `SELECT DISTINCT biz_date FROM folio_items WHERE folio_id = ? AND item_type = 'ROOM' ...`，
  **每张在住单一次**。当前在住 25 单 → 每次打开 `/inhouse` 多 0～25 条 SQL。
  建议：先把候选 `folio_id` 收集成 `IN (...)` 一次查回，按 `folio_id` 分组建 Map，再在内存里补齐日期。

> 另有 3 处曾被启发式误报（`/ar`、`/cashier`、`/channels` 的循环体里出现 SQL 但实际在循环外），
> 已人工核对排除；`/rooms/predict` 的 `allotmentOf` 是纯内存 Map 读取，不是查库。

### 5.2 逐条证据

**场景 1｜同时排同一间房（5 并发，只能 1 个成功）**
- 5 张 PENDING 订单竞争 1 间 VC 房：成功 1、明确拒绝 4（返回 `?err=...` 的中文提示）、500 = 0；
- `booking_rooms` 有效占用 1 条、`bookings` 确认 1 张、`op_logs` 排房日志 1 条；
- 机制：`tx()` 是 `BEGIN IMMEDIATE`，事务内重查 + 乐观锁 `UPDATE rooms SET status=status WHERE status IN ('VC','VD')`。

**场景 2｜同时收同一张账单的钱（不能重复加 / 不能丢）**
- 5 个请求各收 100 全部成功；`payments` 5 笔合计 500、`folios.paid_amount=500`、`balance=500`；
- 5 枚不同 `request_id` 各自只落一笔；`UPDATE paid_amount = paid_amount + ?` 在事务内，无丢更新。

**场景 3｜同时退同一间房（只退一次）**
- 入住单只变一次 `CHECKED_OUT`；`room_logs` 中 `to_status='VD'` 恰好 1 条；保洁任务 1 条；
- 账单 `SETTLED`、余额 0；「退房补收」流水 1 笔 500；
- 其余 4 个请求在事务内发现已退房，按「该笔退房已处理（重复提交已忽略）」返回成功，未重复写库。

**场景 4｜同时收同一房间押金（不丢不重）**
- `stays.deposit=500`（5×100 精确相加）；`payments(kind='DEPOSIT')` 5 笔合计 500；
- `folio_items(item_type='DEPOSIT')` 5 条合计 500；`op_logs` 预收款日志 5 条；
- 无 UNIQUE 冲突（5 枚 request_id 互不相同），事务串行累加。

**场景 5｜同时改同一房间房态（最后一次生效）**
- 5 个请求把 OC 房分别改成 OOO / VD / VC / LOCK / OD，全部无 500；
- 最终 `rooms.status` 等于**最后一条 `room_logs.to_status`**（本次是 VD）；日志恰好 5 条、5 个不同操作人；
- ⚠️ 但 5 条日志的 `from_status` 全是 `OC`：`changeRoomStatus()` 的
  `SELECT → UPDATE → INSERT room_logs` 没包事务，5 个进程都读到了初始状态。
  最终状态正确，但审计链失真（只有 1 次真实流转，却记了 5 次 OC→X）。见 P2。

**场景 6｜同时触发夜审（只跑一次）**
- 3 个店长同时点：1 个 `{ok:true}`，2 个直接抛
  `UNIQUE constraint failed: night_audits.hotel_id, night_audits.biz_date`（生产即 500）；
- `night_audits` 当天**只有 1 条**、营收字段可读，数据没有重复过账；
- 机制：函数开头的事务外查询 `existed` 只能挡住串行重复；事务内没有二次检查，靠表上的
  `UNIQUE(hotel_id,biz_date)` 兜底，冲突没有被翻译成业务提示。

**场景 7｜同时建同一房间同一日期的预订（不能超卖）**
- 5 个并发、同一 `room_id`、同日期：1 成功、4 抛
  `UNIQUE constraint failed: booking_rooms.room_id, check_in_date, check_out_date`（生产即 500）；
- 数据侧：有效占用 1 条、有效 `room_count` 合计 1 ≤ 物理房量 1 → **没有超卖**；
- **附加探针（真问题）**：不指定房间、只订房型（同一房型 1 间可售），5 个并发各订 1 间 →
  **5 个全部成功，`room_count` 合计 5 > 物理 1**。`createBookingAction` 对「只订房型」的行
  完全没有库存校验，串行点击同样会超卖。这是本次最重要的业务缺陷，见 P0。

## 6. 发现的真缺陷

### P0｜只订房型可无限超卖（业务缺陷，与并发无关）

- **现象**：同一房型只有 1 间可售，连续/并发提交 5 张「1 间」的预订，5 张全部落库为 PENDING，
  有效 `room_count` 合计 5 —— 到店无房可排。
- **证据**：`test-concurrency.mjs` 场景 7 附加探针：`可售 1 间，卖了 5 间`；
  5 个请求全部成功，`sold=5 / physical=1`。
- **根因**：`createBookingAction` 只在「指定了 `room_id`」时校验区间冲突；
  对于 `room_id = null` 的房型预订，既不统计该房型区间内已有有效 `room_count`，
  也不和物理房量（扣 OOO/LOCK）比较。`booking_rooms` 的占房唯一索引只约束「已绑定的具体房间」，
  对「未排房型的预订」无效。
- **建议**：
  1. 在**同一个事务内**按 `(hotel_id, room_type_id, 日期区间)` 汇总
     `PENDING/CONFIRMED/CHECKED_IN` 的 `room_count`，与「物理房量 − 维修/锁房」比较，超出即拒绝并给明确文案；
  2. 与 UI 的「可售量」统一走 `lib/room-stock.ts` 口径，避免页面显示可售、提交却超卖；
  3. 加一条并发回归用例（本报告的 7b 探针可直接转成断言）。

### P1｜并发夜审：失败请求 500（数据正确、体验错误）

- **现象**：3 个并发 → 2 个 500：
  `UNIQUE constraint failed: night_audits.hotel_id, night_audits.biz_date`。
- **根因**：`runNightAuditAction` 在事务外查 `existed`，事务内不复查；唯一索引挡住第二个时
  没有 catch，异常直接冒泡成 500。
- **建议**：事务内再查一次（`SELECT ... FOR` 不适用 SQLite，但 `BEGIN IMMEDIATE` 已串行化，
  进事务后复查即可）；或 `INSERT ... ON CONFLICT(hotel_id,biz_date) DO NOTHING` 后判断
  `changes===0` 返回「今日已完成夜审」；同时 catch UNIQUE 兜底。

### P1｜并发建单：被唯一索引拒绝的请求 500

- **现象**：5 个并发同一房间/日期 → 1 成功、4 个 500：
  `UNIQUE constraint failed: booking_rooms.room_id, check_in_date, check_out_date`。
- **根因**：`findRoomConflicts()` 在事务外做冲突校验；5 个请求都通过后进事务，唯一索引兜底，
  但 `createBookingAction` 没有把 UNIQUE 冲突翻译成「房间已被占用，请重新选择」。
- **建议**：把冲突校验挪进 `tx()`（目前 `tx` 是 `BEGIN IMMEDIATE`，天然串行），
  或捕获 UNIQUE 后 `backNew("该房间刚被其他人占用，请重新选择")`；
  与 `assignRoomAction` 已有的处理方式保持一致。

### P2｜并发改房态：`room_logs.from_status` 是旧值，审计链不连续

- **现象**：5 个并发把同一间 OC 房改成不同状态，5 条日志全是 `OC→X`，
  而房间实际只发生了 1 次可用流转（前 4 次被后续写覆盖）。
- **根因**：`src/lib/room-status.ts` 的 `changeRoomStatus()` 是
  `SELECT status` → `UPDATE rooms` → `INSERT room_logs` 三条独立语句，没有事务；
  5 个进程都读到初始 `OC`，各自按 `OC` 判断合法并写日志。
- **影响**：最终房态正确（最后写入获胜），但操作审计不可信（无法还原真实流转顺序/来源）；
  `/logs`、客史、异常检测若依赖 `room_logs` 会误判。
- **建议**：把三条语句包进 `tx()`；或用
  `UPDATE rooms SET status=? WHERE id=? AND status=?` 的 compare-and-set，
  `changes===0` 时重新读取再判断，日志里的 `from_status` 以 CAS 前的读值为准并重试一次。

### P3｜页面响应体过大（潜在 1 秒级问题）

- `reports?r=room-biz-daily` 宽区间返回 **3.60 MB**（46 房 × 730 天），耗时 421 ms；
  按 200 房外推约 16 MB / 1.8 s。建议：
  - 报表默认区间收紧（例如最多 92 天），超出提示「请缩小日期范围或导出」；
  - 逐房×逐日矩阵做分页/虚拟滚动，或后端导出 CSV/XLSX 而不是 HTML 全量铺；
  - 该页 78 条 SQL 合计仅 ~12 ms，优化渲染收益远大于加索引。

### P3｜同页重复查询 / 索引小项

见 3.4（4 条重复 SQL）与第 4 节（`payments`、`channel_orders`、`bookings` 缺索引）。

## 8. 优化建议（按优先级）

1. **P0**：修「只订房型超卖」——事务内按房型统计有效 `room_count` 与物理房量比较（业务正确性优先）。
2. **P1**：`/rooms/forecast` 候选房查询重构（目前 28 ms，是唯一真正 SQL 慢的页面）：
   - 先查「有待排房单位的订单」，再按房型取候选房，避免 `rooms × 全部在售订单`；
   - 加 `bookings(hotel_id, room_id, check_in_date, check_out_date)` 索引；
   - 收紧 `days` 上限（60 天与 365 天响应体一样大，说明当前渲染不随天数收敛）。
3. **P1**：夜审 / 建单的 UNIQUE 冲突翻译成业务提示，消除并发下的 500。
4. **P1**：`room-biz-daily` 的 3.6 MB 响应做区间上限 + 分页/导出。
5. **P2**：补 `payments(hotel_id, folio_id)`、`channel_orders(hotel_id, status)` 索引；
   修 joins 漏 `hotel_id`（`/orders`、`/m/orders`、`/inhouse`、`/night-audit`）；
   把 `date(created_at)` 改成时间范围条件。
6. **P2**：`/inhouse` 的 `missingRoomDates` 批量化，消除 N+1。
7. **P2**：`changeRoomStatus` 包事务，修审计链。
8. **P3**：清掉 4 条同页重复查询；评估 `op_logs` 归档/分区（日志表只增不删）。
