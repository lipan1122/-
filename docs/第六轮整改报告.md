## 附：这轮的方法论收获

清单第一句话是「**页面权限不能代替 Server Action 权限**」。

这轮核实发现：10 个模块共 34 处 `requireUser`、**仅 1 处** `requirePermission` ——
意味着任何能登录的人（含 housekeeper）都能改库存、改账务、改会员等级、红冲发票。

上一轮我在报告里把「206 个 action 的权限分布」写成「有些查看类权限是刻意不接」——
**那个判断是错的**。正确的判断标准是「这个 action 会不会改数据」，
而不是「这个页面有没有守卫」。

新写的 606 条断言现在锁住了这 10 个模块的写操作，其中大量是「housekeeper 调用会被拒」的正向验证，
而不是「源码里有没有 requirePermission」的静态检查。
