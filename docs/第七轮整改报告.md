## 一、修改文件清单

### schema 三处统一（本轮最重要的修复）

| 文件 | 改动 |
| --- | --- |
| `scripts/init-db.mjs` | `booking_no` / `stay_no` / `folio_no` 去掉 `TEXT UNIQUE`，只保留 `NOT NULL` |
| `scripts/schema-full.sql` | 同上 + 补 `idx_stays_no` / `idx_folios_no` 两个组合唯一索引 |
| `scripts/migrate-all.mjs` | 补 `addIndex('idx_stays_no')` / `addIndex('idx_folios_no')`（幂等） |

**为什么这项最重要**：第六轮只重建了**现有库**的表，但**建表模板没改** ——
意味着每装一个新库，全局 UNIQUE 又会回来，第六轮的表重建白做。
这轮修了模板，现在新库安装和旧库升级用同一口径。

`hotels.code` 的全局 UNIQUE **保留**（酒店编码本就该全局唯一，不是单号）。

### 修了表重建脚本的 3 个真 bug

| # | bug | 后果 |
| --- | --- | --- |
| 1 | `hasColumnUnique` 只按 `\n` 切分列定义 | **单行 DDL 判断不出 UNIQUE** → 静默跳过重建 |
| 2 | DDL 生成处 `split("\n")` 逐行替换 | **单行 DDL 时整行不匹配列名** → UNIQUE 没去掉，**但脚本还报「重建成功」** |
| 3 | 验证阶段用同一连接读 `sqlite_master` | `DROP`+`RENAME` 后 schema 缓存未失效 → 明明重建成功却判定失败 |

**第 2 个最危险**：真实库是多行 DDL 所以没暴露，但任何单行 DDL 的库会被
「重建成功但约束还在」。现在 `test-schema-rebuild-idempotent.mjs` 专门覆盖它（造单行 DDL 的库）。

## 九、仍存在的已知问题

### D-1 allotment 语义未经酒店确认（阻断 OTA 联调）

当前实现：`sellable = min(物理可卖上限, allotment) − 在住 − 预订`
若酒店认为 allotment 是「当天剩余可卖数量」而非「总放量上限」，算法要改。

### D-2 Server Action 无权限时用户看到错误页

`requirePermission()` 是 `throw`，Next 16 渲染成错误页，用户看不到「无权执行」。
安全上没问题（无权限请求确实被拒且零副作用，354 条断言验证），但体验差。
修法：拆 `requirePermission`（throw）/ `checkPermission`（返回结果），涉及 100+ action。

### D-3 商超购物车多商品只结算第一件（改动前就存在）

`ShopPOS` 传 `item_id = cart[0].id` + `qty = 总件数` —— 购物车里有**多个不同商品**时只结算第一件
（多件同商品没问题）。修它要同时改 `page.tsx` 的购物车模型，本轮范围外。

### D-4 `shop/page.tsx` 的 `submitOrder` 成了死代码

`ShopPOS` 改为直接调 server action 后，页面传下来的 `submitOrder` 不再生效。
`onSubmit` 参数降级为兼容占位，注释里写了原因与清理建议。

### D-5 `sellAction` 成功跳 `?ok=`，页面只读 `msg/err`（挂房账横幅不显示）

改动前就存在，本轮范围外。

### D-6 权限矩阵分组名显示英文

新增的 `breakfast` / `invoice` / `member` 分组在设置页显示英文而非中文。
`settings/page.tsx` 的 `PERMISSION_MODULE_LABELS` 补三行即可。

## 附：本轮的方法论收获

第七轮暴露的问题模式是「**修了存量，没修模板**」：

- 第六轮重建了现有库的三张表，但 `init-db.mjs` / `schema-full.sql` 里的建表语句
  还是 `TEXT UNIQUE` —— 每装一个新库，问题就回来
- 同理 `invoice.ts` 的 `ensureInvoiceSchema` 也要加索引，否则「克隆仓库直接 dev」会少约束

这轮把「同一个约束必须在**所有产生它的地方**都改」当成检查项：
`init-db`（新库）+ `schema-full.sql`（懒建兜底）+ `migrate-all`（旧库升级）+
应用层 `ensure*Schema`（运行时兜底）+ 真库（已执行）。

另一个发现：**测试造的数据形态要和真实一致**。
`hasColumnUnique` 和 DDL 生成的两个 bug 都只在**单行 DDL** 上暴露，
而真实库是多行 —— 意味着如果只测真实库，这两个 bug 永远不会被发现。
`test-schema-rebuild-idempotent.mjs` 特意造单行 DDL 的旧格式库来覆盖它。
